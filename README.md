## 这是什么

一个从零手写的仙侠放置（挂机）游戏，**不是只搭了个能跑的壳**。

放置类最容易糊弄的两处是「时间」和「战斗」——前者常靠定时器扫全服，后者常把结果丢给前端。这个项目在这两处都做了正经处理：

- **离线收益不靠轮询** —— 惰性结算：没有定时器、不遍历全服，收益由 `now - last_settle_at` 算出；落库节流到 60 秒一次，用 `last_settle_at` 做 CAS 守卫，**8 个并发请求同时打只会发一份钱**（探针里有这条断言）；离线超过 12 小时的部分按 20% 折算。
- **战斗结果可信** —— 服务端权威 + **种子可复算**：随机种子与双方面板一并入库，同一份输入能完整重跑整场战局，这是查作弊与客服补单的地基。
- **伤害按每条灵根分别判定五行克制** —— 系数不是写死的常数。同一套道体打不同五行，系数在 0.75~1.30 之间浮动；而且**公式本身在游戏内对玩家公开**。
- **账目对得上** —— 货币流水只有一个记账口径：每行的 `delta` 只反映它自己的 `reason`，结算永远单列，按 `delta` 求和就能对账。
- **数值可维护** —— 试炼塔 15 层的怪物数值不是手填的，由 `scripts/tune-tower.js` 按「预期境界档」反推；探针再用**真实战斗内核跑 200 个种子**校验每层胜率，杜绝"标定器自己认定的参考玩家却打不过"这种硬墙。
- **回归有闸门** —— `smoke-test.js`（59 项完整闭环）与 `bug-probe.js`（203 项对抗性探针：并发、边界、越权、原子性、数值平衡）。

> 定位是**学习与自用向的完整 MVP**，不是生产系统。已知边界（试炼塔无每日限次、排行榜实时 `COUNT`、无日志归档等）都写在[第十节](#十已知边界)里，没有藏。

| 洞府 | 十级，逐级提升灵石加成，成本随境界经济同步上调 |

## 三、伤害公式（逐条灵根判定）

这是本项目的核心设计，页面上「修炼 → 伤害公式推导」会把下面每一步用你自己的数值代入展示出来。

**攻方（我方打怪）**

```
贡献_e = 克制系数(e → 目标五行) × 灵根值_e / 满值
攻击灵根系数 = Σ 贡献_e ÷ 有效灵根条数 × 平衡系数
```

- 克制系数：克制 ×1.30、被克 ×0.75、其余 ×1.00（金克木、木克土、土克水、水克火、火克金）
- 平衡系数 `rootMulScale` 默认 **1.9**，用来把整套数值锚定在原来的强度上（随机五灵根角色 ≈ 1.0）
- 「有效灵根」= 值不为 0 的灵根，所以**灵根越集中，平均值越高**（不被低值灵根稀释）

**三条设计意图的实测结果**（目标为「木」属性）：

| 道体 | 攻击灵根系数 |
|---|---|
| 单金灵根，值 95（克制） | **2.47** |
| 金木双灵根，各 95 | 2.19 |
| 混沌灵根（五条全满） | **2.85** ← 最高 |
| 单土灵根，值 95（被克） | 1.43 |
| 金灵根，值 20 | 0.52 |
| 随机五灵根（均值 50） | ≈ 1.00 |

**守方（怪打我）**

```
防守灵根系数 = Σ 克制系数(对方五行 → 灵根_e) ÷ 有效灵根条数
```

刻意**不加权、不缩放**：灵根越多越接近 1.0（稳），单灵根等于把身家押在一种五行对抗上（可能扛揍，也可能被克）。
实测：单土灵根被木系怪打 = 1.30（吃亏），五灵根 = 1.01（中性）。

**最终伤害**

```
每击 = (攻击 × 攻击灵根系数 × 0.95~1.05 波动 − 对方防御 × 0.6) × 暴击(10% 概率 ×1.5)
```

五灵根全为 0 的「凡体」取保底系数 0.30 —— 没有灵根反而更弱，避免"全散成 0"变成最优解。

### 本轮新增功能的规则细节

**单条灵根洗练**（`POST /api/role/roots/reroll` + `/confirm`）

- 每次只洗一条灵根，其余四条不动；数值区间 `world.rootRoll`（默认 5–95）。
- **保底**：同一条灵根每洗 5 次（`world.rootPityEvery`）触发一次，那次从 `[当前值+1, 上限]` 取值，必定高于原值。计数按灵根分别记录在 `role.root_pity`。
- 结果不会直接生效：服务端摇完先存进 `role.root_pending`，玩家点「保存新灵根」才写入 `role.roots`，点「保留原本灵根」则维持原值。**灵石在洗练那一刻就扣掉，放弃不退款。**
- 有待确认结果时不允许继续洗，避免连点把结果覆盖掉。
- 客户端无法伪造数值：它只发"我要洗哪条灵根"，值由服务端摇并存着。

**出售**：单价 `floor(price × world.sellRate)`，默认 0.7；已装备不可卖；原子扣减，数量不足直接拒绝。

**排行榜**：`ORDER BY realm DESC, realm_level DESC, exp DESC, id ASC`，只统计 `account.status = 1` 的账号；走 `role.idx_rank` 索引。榜外时也会返回"我的名次 + 我的成绩"，玩家才知道离上榜差多少。

**商店八档与价格**：法宝与功法一一对应八个大境界。价格口径是「**到达该境界时的实际产出 × 30~40 分钟**」（到达时产出 = 基础产出 × 层数 1.3 × 灵根 1.15 × 洞府该档 × (1 + 上一档功法加成)）。

这条口径很关键：产出随境界涨约 6.7 倍，如果价格只按基础产出定，后期会越买越便宜（曾经筑基要 88 分钟、大乘只要 2 分钟，"灵石溢出"就是这么来的）。现在各档买入耗时收敛在 **30~88 分钟**，探针里有断言守着。

| 对应境界 | 法宝 | 功法 |
|---|---|---|
| 炼气 | 青锋剑 800 | 引气诀 500 |
| 筑基 | 护心镜 30 万 / 玄铁重剑 40 万 | 玄天心法 35 万 |
| 金丹 | 乾坤鼎 250 万 / 紫霄神剑 300 万 | 太虚道经 280 万 |
| 元婴 | 赤霄焚天戟 2000 万 | 九转元功 1800 万 |
| 化神 | 太乙玄光镜 2.24 亿 | 大衍神通 1.68 亿 |
| 炼虚 | 混沌青莲 28.2 亿 | 无极真解 21.2 亿 |
| 合体 | 周天星斗盘 364 亿 | 混元道果 273 亿 |
| 大乘 | 鸿蒙紫气钟 5150 亿 | 造化玉牒 3860 亿 |

**悟道石**是消耗品，加成持续到本次突破成功为止（失败不清零），所以按「该境界约 1 分钟产出」定价（500 / 5 千 / 4 万 / 45 万 / 550 万 / 7 千万 / 9 亿 / 130 亿）。若按"一次性"的价格卖，它相对"省下的那点失败修为"会贵几十倍，等于死道具。

**试炼塔的数值标定**：`scripts/tune-tower.js` 按「每层对应的预期境界档」反推怪物数值——参考玩家是该档境界中期 + **上一档**的法宝与功法，目标是约 8 回合击杀、损失约 40% 气血。

- 刻意的"上一档装备"：这样刚升入本境界的人，不必先攒够本档装备就能清掉上一档的层（例如化神期带金丹/元婴装可以稳过前 8 层），符合"每个大境界对应约 2 层"的预期。
- **克制系数必须按每层的五行真实算**（`attackRootMul`/`defendRootMul`），不能用固定常数：同一个道体打不同五行，攻方系数在 0.75~1.30 之间浮动。用常数会把某些层标成必败墙（曾经第 8 层攻方 0.975 / 守方 1.075，被标成"优势"而实测胜率只有 0.5%）。
- **单调修正**：五行换算会让个别层反而变弱（第 6 层曾比第 5 层还软），标定结束后做一次"只升不降"的修正，保证层数越高越强。
- 同时保住天花板：低两个档次的玩家打不过高档层（实测金丹期打第 15 层每击只有 1 点伤害）。
- **失败惩罚**：每层 `failExp = 该层奖励修为 × 0.35`，同档第二层更硬 → 奖励与惩罚同步更高，所以 15 层的数值两两不同；折算下来最重约 52 秒挂机产出，修为不够时只扣到 0。
- `scripts/bug-probe.js` 会**直接调用 `core/battle.js` 跑 200 个种子**统计每层胜率，要求参考玩家 ≥90%，这是"塔能不能打"的唯一判据（只看推演的"优势/劣势"曾经把 0.5% 胜率的层判成优势）。
- 改平衡请改脚本再 `node scripts/tune-tower.js --write`，不要手改 `stage.json`。标定脚本会导出参考玩家与映射表给测试复用，保证两边永远是同一个参考。

**行动记录**：写在 `log_action` 表（与 `log_currency` 分工：流水给运营对账，行动记录给玩家看"我刚做了什么"）。档案接口 `GET /api/role/profile` 会顺带带回最近 15 条，所以右侧行动区**不需要额外请求**，跟着 5 秒轮询自动刷新。

## 四、四个值得注意的设计

### 1. 惰性结算（性能地基）

不跑定时器、不遍历全服玩家。每次请求用 `now - last_settle_at` 算出这段时间该发多少：

```js
// server/src/core/settle.js
const effective = Math.min(seconds, capSeconds) + Math.max(0, seconds - capSeconds) * 0.2;
const stone = Math.floor(derived.stonePerSec * effective);
const exp   = Math.floor(stone * config.settle.expRate);
```

前端每 5 秒轮询档案，但**服务端只在累计满 60 秒时才真正 UPDATE**，两次结算之间由前端按 `stonePerSec` 本地插值，数字照样在跳。

### 2. 并发安全：版本号 + 时间戳双重守卫

轮询结算不是事务，可能和玩家操作（突破/购买）撞车。所以落库时带守卫：

```sql
UPDATE `role` SET `spirit_stone` = `spirit_stone` + ?, `last_settle_at` = ?, `version` = `version` + 1
WHERE `id` = ? AND `last_settle_at` = ?
WHERE `id` = ? AND `last_settle_at` = ? AND `version` = ?
```

`affectedRows = 0` 就说明别人已经结过账了，直接放弃本次发放 —— 不会重复发钱。
玩家主动操作（突破、购物、打塔、服丹）则统一走 `SELECT ... FOR UPDATE` 行锁事务。

### 3. 服务端权威 + 种子可复算的战斗

`server/src/core/battle.js` 是**纯函数**：给定双方属性和一个 `seed`，必然产出同一份战报。

```js
const report = battleCore.simulate(player, monster, seed);
// seed 同时写进 log_battle，任何时候都能复算出同一场战斗
```

客户端只发"我要打第 N 层"，伤害、暴击、胜负全部服务端算。将来换成卡牌回合制，只替换 `simulate` 即可，其余不动。

### 4. 货币流水

任何资源增减都写 `log_currency`（变动量 + 变动后余额 + 原因）。这是运营期对账、回滚、客服补单的救命稻草，`见闻录` 页面直接读它。

## 七、怎么调数值

改 `server/src/game/*.json` 就行，代码里没有任何硬编码数值，改完重启后端生效：

- `realm.json` — 境界名、每层灵石产出（`stonePerSec`）、升级所需修为、突破基础成功率
- `item.json` — 物品、价格（灵石）、效果（`stoneBonus` 是挂机产出加成，`breakBonus` 是悟道石加成，单位万分比，`realm` 是对应大境界）。法宝与功法的战斗数值在本轮整体上调了 2.5 倍
- `stage.json` — **不要手改**，跑 `node scripts/tune-tower.js --write` 由脚本重算
- `world.json` — 五行相克、灵根区间 `rootRoll`、洗练保底间隔 `rootPityEvery`、洗练递增价 `rerollRootsCost`（base + base×factor×(值/满值)²，当前 base=3000 / factor=50 → 3000~15.3 万）、回收比例 `sellRate`、洞府成本 `cave`、突破惩罚
- `world.json → combat` — 伤害公式的全部系数：`elementAdvantage/Disadvantage`（克制 1.3 / 被克 0.75）、**`rootMulScale`（平衡系数，调这个等于整体调攻）**、`minRootMul`、`emptyRootMul`（凡体保底）、`chaosMul`（混沌加成）

节奏相关的运行时参数在 `server/.env`：`SETTLE_MAX_HOURS`（离线上限）、`SETTLE_MIN_PERSIST_SECONDS`（落库节流）、`SETTLE_EXP_RATE`（灵石转修为比例）。

当前节奏：约 18 分钟炼气→筑基，后续每境界数小时，满级约 45 小时挂机量。

### 第二轮（独立代码审查后）

这一轮把两个子代理的独立审查结论逐条核实后再动手，**误报的没有改**。

| # | 问题 | 后果 | 修法 |
|---|---|---|---|
| 14 | 令牌失效时前端永不清 token（**致命**） | 后端鉴权失败是 HTTP 401，走 axios 的 error 分支，而清 token 的代码写在成功分支里 = 死代码 → 路由守卫看到 token 还在，把跳转弹回 `/game` → 永久卡在加载遮罩，且「退出」按钮在 `v-if` 里面，用户**无路可走**，只能手动清 localStorage | 在 error 分支识别 401/1002，**先清 token 再跳登录**；遮罩上补「重新登录」出口 |
| 15 | 结算基准写成 `NOW()` 而不是计算收益时的时刻 | 发放的区间与推进的基准有偏差（写库延迟 + 应用/数据库时钟差），每次结算都悄悄少发一点点 | `computeSettle` 返回计算时刻，落库写这一时刻 |
| 16 | 结算 CAS 把 `version` 也当条件 | `version` 是整行版本号，换装备等无关写入都会让它变，合法结算被白白丢掉 | CAS 只用 `last_settle_at`（它本身就是单调时钟） |
| 17 | 流水记账口径 5 个入口 3 种写法 | 「突破」那条会把结算收益混进 delta，出现**「突破失败但 delta 为正」**的自相矛盾流水，按 delta 求和对账必然出错 | 抽出唯一的 `currencyLogs()`：每条流水的 delta 只反映自己的 reason，结算永远单列 |
| 18 | 坊市列表返回未结算的余额 | 与购买时的扣款口径不一致，界面显示与"买得起吗"打架 | `shop.list` 也带上未落库结算 |
| 19 | `stageId` 非法时报「该层不存在」；且若塔层 id 不连续，`findIndex` 返回 -1 会把 `if (idx > 0)` 当成第一层**绕过解锁校验** | 参数错误被伪装成资源不存在；改配置时可能开出越级挑战漏洞 | 先校验整数，再显式拦 `idx < 0` |
| 20 | 断线时前端仍按 `stonePerSec` 无限估算 | 数字会虚涨到几小时的产量，恢复瞬间大幅回退 | 插值上限夹在 12 秒，并在连续 3 次失败后顶部显示「已失联」 |
| 21 | 轮询无并发/顺序保护 | 慢响应时先发后到，旧档案覆盖新状态；登出后迟到的响应还会把旧账号档案写回 | 加在途去重 + 档案序号，迟到响应直接丢弃 |
| 22 | `formatNum` 在 9999.9999万 这类边界 | 显示成「10000.00万」，看着像溢出 | 四舍五入后进位到上一档 |
| 23 | 新建角色只校验 `profile.role` | 万一后端漏发 `derived`，模板报错后组件渲染不出 DOM 且**不会自愈**（整页空白） | 校验 `role` + `derived` |
| 24 | 生产环境用默认 `JWT_SECRET` 也能静默启动 | 默认密钥是公开的，等于全服账号可被接管 | 生产环境拒绝启动，开发环境打警告 |
| 25 | 登录页在请求飞行中按回车可重复提交 | 发两次登录请求、两条提示 | `submit` 加 loading 闸门 |
| 26 | 零碎清理 | —— | 删掉未使用的 `dayjs`/`echarts` 依赖、`state.timer`、无用变量；profile 轮询日志不再刷屏；`humanDuration(61)` 不再显示成「1分」；`expRate`/`levelsPerRealm` 改为读配置而非硬编码 |

**核实后判定为误报 / 不成立的**（因此没有改代码）：

- 「登录接口不返回完整档案，`SET_PROFILE` 静默失效」——**误报**。`authService` 只返回 token，但 `auth.route.js` 在路由层合并了完整档案；实测登录响应确实带 `role/derived/equip/settle`（见冒烟测试第 7 项与代理实测输出）。
- 「`updateRoleFields` 绝对盲写会丢失更新」——**当前设计下不可复现**。子代理自己也标注了"用真实代码路径无法复现"：动作事务的 `SELECT ... FOR UPDATE` 会挡住并发的结算 UPDATE。仅在多实例/读写分离/改隔离级别后才成立，属于需要在架构变化时重新评估的风险，不是当下的 bug。
- 「`limit` 负数打成 500」「洞府升级不写流水」——子代理读到的是修复前的版本，上一轮已修。
- 「试炼塔没有每日次数限制」——**设计取舍**，已记录在「已知边界」。
- 「BIGINT 与 JS Number 精度」——当前数值量级（最大约 1.7e11）远低于 2^53，不成立。

### 第三轮（针对本轮改动的独立审查 + 复算）

这一轮同样先自己复算再动手，**误报的没有改**。

| # | 问题 | 后果 | 修法 |
|---|---|---|---|
| 27 | 标定脚本用固定克制系数 `REF_MUL = 1.2`（**高**） | 同一个道体打不同五行，攻方系数在 0.75~1.30 浮动。第 8 层真实攻方只有 0.975、守方 1.075，双重不利 → 用 2000 个种子实跑，**标定器自己认定的参考玩家在第 8 层胜率只有 0.5%**，是硬墙不是难度（其余层 100%） | 标定改用 `formula.attackRootMul/defendRootMul` 按每层五行真实算；第二层倍率从 1.35/1.15 收到 1.15/1.08；目标改为 8 回合 / 40% 气血 |
| 28 | 推演的「优势/劣势」被当成平衡判据 | 上一轮探针就是用它判"每档都能过"，于是 0.5% 胜率的层也全绿——**测试通过 ≠ 数值健康** | 探针改为**直接调用 `core/battle.js` 跑 200 个种子**统计胜率，要求 ≥90%；另加"低两档玩家不得过关"的门槛断言 |
| 29 | 五行换算让第 6 层比第 5 层弱（**中**） | 层数越高反而越软，破坏"往上爬"的直觉 | 标定末尾做一次单调修正（只升不降），探针断言五列严格递增 |
| 30 | 经济曲线倒挂：越后期越便宜（**高**） | 价格按"基础产出"定，但产出随境界涨 6.7 倍而价格没跟上 → 筑基买齐要 **88 分钟**、大乘只要 **2 分钟**，"灵石溢出"的根因 | 价格口径改为「到达该境界时的实际产出 × 30~40 分钟」，全档收敛到 30~88 分钟，探针有断言守着 |
| 31 | 悟道石在"突破一次即清零"规则下成了死道具（**中**） | +5% 且只保一次，而失败成本折算只有几千灵石、石头却卖几万——**贵了几十倍，理性玩家永远不会买** | 每颗改为 +15%，价格降到「该境界约 1 分钟产出」；加成**持续到突破成功为止（失败不清零）**，文案同步说明 |
| 32 | `/api/role/logs` 的 `page` 无上限（**中**） | `?page=4294967295` 会算出天量 OFFSET，逼 InnoDB 全量扫描，几个并发就能拖住连接池 | 页码夹在 1..1000 |
| 33 | 日志 `ORDER BY id DESC` 与索引 `(role_id, created_at)` 不匹配 | 用不上索引顺序 → 每次翻页 filesort，日志越涨越慢 | 排序改为 `created_at DESC, id DESC`，与索引完全对齐（3 处） |
| 34 | `log_battle.detail` 写全量逐回合战报，却没有任何读路径（**低**） | 每次挑战按 60 条事件写几 KB JSON，纯存储开销 | 改为只存"复算所需输入 + 摘要"（seed / 双方面板 / 灵根判定 / 结果），量级小一个数量级且更便于查作弊 |
| 35 | 前端样式被 Element 特异性压掉（**中**） | 表格单元格分隔线仍是 `#EBEEF5` 亮色；`el-tag--success/info/warning` 是浅底低对比（2.0~2.8:1）；`el-radio` 白圈选中变蓝；分页器"共 N 条"仍 `#606266` | 所有覆盖按 Element 的真实选择器（`td.el-table__cell`、`.el-tag.el-tag--success` 等）**同规格重写** |
| 36 | 翻页请求失败后分页器与数据错位（**低**） | 分页器停在第 2 页、内容还是第 1 页，只能再点一次自愈 | 失败时用 `syncKey` 强制分页器重建以回滚页码 |
| 37 | 突破率构成在夹取时算不平（**低**） | 大乘高层 `40% − 40% = 0%`，但实际有 5% 保底，等式少 5 个点 | 面板显式列出「下限/上限修正」一项 |
| 38 | `/game/config` 拉取失败不重试（**低**） | 塔层对手列永久"未知"、境界表永远空白，只能整页刷新 | 轮询时发现 config 为空就补拉 |
| 39 | **测试工具自身的缺陷**：冒烟测试不检查端口占用 | 3000 上还跑着开发服务器时，`listen` 失败被吞掉，请求打到旧进程 → **测的是旧代码，回归被悄悄掩盖**（这一轮真的踩到了：配置已改而测试仍报旧值） | 启动前做 TCP 探测，端口被占直接报错退出 |
| 40 | 并发结算的断言过严 | 8 个并发请求各按"自己那一刻"算结算窗口，彼此可能差 1~2 秒产出，断言"完全相等"会偶发误报 | 改为断言彼此差额不超过 3 秒产出（真正要守的是"没有少发/多发一整笔"） |

**核实后判定为误报 / 不成立的**：

- 「`preview()` 漏乘守方灵根系数」——**误报**。`simulate()` 里玩家用 `attack.mul`、怪物用 `defend.mul`，而 `preview()` 的 `playerHit = atk × attack.mul`、`monsterHit = atk × defend.mul`，两侧口径本来就一致（复核 `core/battle.js` 的伤害表达式）。真正错的是**标定脚本**（第 27 条），推演本身没问题。
- 「`pages` 在无记录时返回 1 与空列表矛盾」——保留。约定"至少 1 页"，且前端在空列表时根本不渲染分页器（显示「暂无记录」），无实际影响。
- 「`preview(stageId)` 非法参数静默回落到第 1 层」——保留。这是只读推演接口的有意设计（已写进接口说明并有断言覆盖），`challenge` 才需要严格报错。
- 「`failExp` 只惩罚已卡关的人」——设计取舍。惩罚恒为该层奖励的 35%（赢一次得 3 倍于输一次的代价），折算最重 52 秒挂机产出，且修为不足时只扣到 0，不存在死亡螺旋。

## 十、已知边界

- 单角色单账号，未做多角色切换。
- 试炼塔无每日次数限制（放置类可接受，需要限次时加一张 `role_stage_daily`）。
- 排行榜每次请求实时 `COUNT` 一次我的名次，玩家量上千后应改缓存或 Redis 有序集合。
- 出售没有每日额度或冷却，理论上可以反复买入再卖出——但 7 成回收本身就堵死了套利空间。
- 灵根洗练的待确认结果不会过期，会一直挂着直到玩家点保存或放弃（不影响其他玩法，只是不能再洗）。
- 散灵丹可以反复用来把灵根散到 0，但**五条全散会变成"无灵根"凡体（系数 0.30），是最弱的形态**，不是最优解。
- 悟道石加成会一直帮到你突破成功为止，成功一次后清零，所以它是"给某一次突破上保险"的消耗品，不能囤着一直吃。
- 「最多再买 N 颗」是按当前层数与保底实时算的：每突破一层，基础成功率会降 5%，于是又腾出新的可买空间。
- 日志表用 `(role_id, created_at)` 索引并按 `created_at DESC, id DESC` 排序；页码上限 1000 页，再深的分页没有意义（也没有归档，见上）。
- `log_battle` 只存"复算所需输入 + 摘要"（seed、双方面板、灵根判定、结果），不存逐回合明细；要完整回放就用 seed 重跑 `core/battle.js`。
- 装备没有境界限制：理论上可以攒钱提前买下一档法宝，但价格按该境界产出标定，提前买等于几十小时白挂。
- 试炼塔的数值是按"该档境界 + 该档装备 + 灵根系数 1.2"标定的，所以**灵根很集中的玩家会比同境界的人多打好几层**——这是设计要求，不是 bug。
- 战斗推演的每击伤害用的是「期望值」（暴击按概率折算），实际战报会有 0.95~1.05 的波动与暴击。
- `log_action` 与 `log_currency` 只增不删，没有归档策略；上量后需要按时间分表或定期清理。
- 前端是 Element UI 整包引入，vendor 包约 978 KiB（gzip 约 270 KiB）。要做首屏优化就用 `babel-plugin-component` 按需引入。
- 前端未做移动端适配，当前按桌面端 1280+ 布局（左侧角色栏 + 中间页签 + 右侧行动区）。
